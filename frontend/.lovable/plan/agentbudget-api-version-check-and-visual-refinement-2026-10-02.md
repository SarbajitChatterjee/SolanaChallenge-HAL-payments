# AgentBudget: API version check and visual refinement

## What is confirmed
- The live API returns `version: "1.1.0"` from `/health` and allows both the published and preview site origins. The published Rules page currently displays **API 1.1.0** after loading. I could not inspect the private preview URL externally because it redirects to Lovable sign-in.
- The footer displays “API version unknown” whenever its health request has no data, including while the request is still loading. Settings tests the address typed in the dialog separately and labels every failed network request as a sleeping server, even when the cause is different. The local sandbox preview shows “unknown”; that alone does not establish a fault on the published site.
- The Rules page currently uses large curved panels, bordered boxes inside agent cards, and another full panel around Items and Change history. Those layers make the rules harder to scan.

## Plan
1. **API version:** Reproduce the Settings “Test connection” flow against the saved, live API address in the relevant browser context. Check the request’s actual origin, response, and browser error before changing anything. Keep the existing direct browser-to-API approach; do not add localhost to allowed origins, introduce a proxy, or change the backend. If the issue is a frontend error, fix only the health-test/version display and its misleading status text. If the API rejects the actual origin, report that exact origin and evidence rather than disguising it as a server wake-up delay.
2. **Rules workspace:** Use the chosen **architectural grid** direction, tempered by your locked **refined AgentBudget palette** and **Sora/Manrope** typography. Add an in-page collapsible control rail for Agents, Items, and Change history (compact icon rail when collapsed; compact section selector on small screens). Keep all existing rules data and actions. Give each agent one sharply framed surface with an aligned, integrated three-column budget strip, concise allowed-item chips, and consistent Edit / Archive / key placement. Use clear table rows for Items and compact change rows for History, with empty, loading, and error states designed as carefully as populated data. Do not invent ranks, counts, or labels from the concept preview.
3. **Less-curved design across the app:** Reduce card, dialog, input, tab, navigation, and button radii to a consistent boxier scale; reduce nested heavy borders and hard-shadow offsets where they create visual noise. Retain the existing sky/yellow/mint meaning, readable USDC values, obvious current-page and destructive states, and the dot-grid identity. Preserve purposeful motion and reduced-motion support.
4. **Cosmetic usability pass:** Review Home, Live demo, Connect your agent, Early access, Rules, menus, and dialogs for visual hierarchy, action placement, spacing, contrast, and mobile readability. Make presentation-only adjustments that support immediate scanning and natural next actions; do not change copy meaning, API contracts, purchases, tour behavior, forms, or any backend logic.
5. **Verify:** Check the published health/version path and the Settings result, then inspect all routes at desktop and mobile widths for overflow, hierarchy, visible actions, and loading/error presentation. Check the preview build signal before reporting completion.

## Technical boundaries
All network requests remain in `src/lib/api.ts`. Changes stay in frontend presentation files plus the narrowly scoped health-test/version UI if evidence supports it. No database, auth, backend, proxy, or new product functionality. Shared visual tokens live in `src/styles.css`; route metadata stays intact.
